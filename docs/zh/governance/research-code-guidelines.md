# 研究代码指南

本仓库是研究代码。首要目标是获得可信且可复现的实验结果，而不是追求生产系统式的抽象。

## 贡献稀疏方法

新增或重构一等 SparseEngine 稀疏方法时，应把方法特定的运行时状态保存在 `src/sparseengine/engine/cache_manager/` 中，保持 `src/sparseengine/layers/attention.py` 的通用性，并尽可能通过共享缓存管理器接口接入新行为。

## 研究代码优先级

首要目标：

1. 让实验可复现。
2. 让结果易于验证。
3. 保持实现精简且易读。
4. 避免隐藏失败。

工作规则：

- 优先选择简单、显式的代码，而不是重抽象框架。
- 除非必要，否则不要引入新依赖；确有必要时，应记录原因。
- 除非明确要求，否则不要添加宽泛的回退逻辑、静默异常处理或自动恢复路径。
- 不要用默认值、随机替代项、空输出或仅告警行为掩盖错误。
- 缺少必需文件、配置、checkpoint、数据集或 API key 时，应快速失败并给出清晰错误信息。
- 将改动限制在所请求的实验或缺陷范围内。
- 除非明确要求重构，否则保留现有实验语义。
- 仅为不直观的研究逻辑、张量形状、算法选择或论文特定细节添加注释。

## 可靠性规则

首要目标是获得可信的实验结果。

1. 不要隐藏失败。缺失文件、错误配置、API 调用失败、解析错误和指标错误都必须显式呈现。
2. 除非明确要求，否则不要添加回退行为。所有回退都必须由用户选择启用、写入日志，并反映在最终结果中。
3. 每个被评估样本都必须具有明确状态：`success`、`invalid_input`、`model_failed`、`parse_failed`、`metric_failed` 或 `skipped_by_policy`。
4. 分别保存原始输出、解析输出、逐样本结果和聚合指标。
5. 除非明确要求，否则不要更改指标定义或样本纳入规则。
6. 限制所有重试、循环、API 调用和解析尝试的次数。
7. 在配置、数据集、模型加载、解析和指标边界验证输入。
8. 保存足以复现实验的运行信息：配置、命令、模型、数据集 split、prompt、decode 参数、seed 和样本数。
9. 实施最小且正确的改动。避免无关重构、新依赖和接口重命名。

## 基准测试产物

对于基准测试脚本，预期的输出布局应确保失败和评分过程可审计：

- `raw_outputs.jsonl`：原始模型响应和生成元数据。
- `parsed_outputs.jsonl`：解析后的预测和解析器状态。
- `per_sample_results.jsonl`：样本 ID、输入元数据、预测、目标、正确性和显式状态。
- `aggregate_metrics.json`：根据逐样本结果计算的最终指标。
- `run_info.json`：命令、环境、模型路径、数据集路径、split、样本数、decode 参数、seed、方法参数和相关环境变量。

如果明确启用了回退，逐样本结果和聚合元数据必须记录哪些样本使用了回退。本仓库不接受静默回退产生的结果。
