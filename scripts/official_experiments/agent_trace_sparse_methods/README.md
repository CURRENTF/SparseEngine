# Agent trajectory serving comparison

The completed 8,000-request measurements and validity decisions are in
[RESULTS.md](RESULTS.md), with machine-readable data in [results.json](results.json).

This experiment replays 100-agent SWE-bench Lite traces against
GLM-4.7-Flash. The trajectory inputs were generated by GLM-4.7-Flash. The
original trace has 6,490 recorded non-streaming requests; the longest-turn
subset has 8,000.
For each nonterminal turn, the server samples normally and then replaces the
sampled token with the tokenized recorded answer before that token enters the
sequence state and KV cache. The next input therefore matches the actual
server-side generated history. The last turn keeps its recorded completion-token
count because no later prompt needs to match it. Tools are not executed. This
is a forced-transcript serving comparison, not a MiniSWE quality score.

The standard public corpus is the appendable 8,000-request trace on
[`JitaiHao/SWE-lite-trace100` main](https://huggingface.co/datasets/JitaiHao/SWE-lite-trace100).
Its verified revision is `6bce0bb91ba68948248fd44b914ef77664b6b4e6`;
pin that revision and its published manifest hash
`f0506d5769518601292ef85f7a6810fe3b7967229793b72d4c3d7249ca8ac3b5`
for reproducible runs.
The local and AutoDL preparation copy has source manifest hash
`e9449fdabd7bb8d0d045be0b1820f9fe9ecf4b2c44c1e5f943910daa60a0b001`.
Publishing removes private provenance fields and changes the manifest hash;
current preparation results must stay associated with the source hash.

## Longest-trajectory subset

The original 100-agent trace selected the first 100 IDs in the source run's
`instances.txt`. A separate trace selects 100 from the same 300-instance
GLM-4.7-Flash run with `--selection longest_turns`. Length is the number of
successful model requests recorded in each agent trajectory. All 100 selected
agents have 80 turns, for 8,000 requests. Since 157 agents have 80 turns, ties
keep the frozen `instances.txt` order. The selection does not filter by
terminal status.
For the performance rerun, exclude `matplotlib__matplotlib-23476`: its first
assistant response was discarded by the agent after an invalid tool call, so
the following prompt cannot append to that response in Chain Cache. The next
80-turn candidate in source order, `scikit-learn__scikit-learn-25638`, replaces
it. The resulting trace still contains 100 agents and 8,000 requests; its
manifest records the explicit exclusion. Preserve the initial selection as a
separate artifact.
The new trace is a different workload; compare methods only after rerunning
their matched baseline against its manifest. Keep the older 6,490-request
results associated with their original trace hash.
For the 8,000-request rerun, the requested matrix is Vanilla, QuEST, and
OmniKV at C=40, plus SnapKV and H2O at C=80. There is no C=80 Vanilla
measurement in this matrix, so do not report a C=80 speedup versus Vanilla.

To reproduce the selection, pass the original 300-instance run directory and

## Frozen protocol

- The model checkpoints, trace directory, output directory, two idle GPUs, and
  conda environment are explicit launch arguments. Keep both GPU UUIDs, model
  checkpoint, trace manifest hash, and client location fixed within a pair.
- Set `AGENT_TRACE_SCRATCH_BASE` to a node-local writable directory for Triton,
  CUDA, FlashInfer, and temporary files. Keep case outputs under the persistent
  output root; a remote filesystem compiler cache can fail while loading a
  generated shared object.
- Use the method configuration in
  [`../chain_cache_miniswe/setting.json`](../chain_cache_miniswe/setting.json).
  The case runner calls its `prepare` entrypoint. For each case,
  `max_decoding_seqs=max_num_seqs_in_batch=C` and
  `max_num_seqs_in_gpu=1.5*C`. The agent concurrency is also `C`.
- This H20 campaign compares vanilla, OmniKV, QuEST, SnapKV, and H2O at C=40.
  Exploratory C=100 runs of vanilla, SnapKV, and H2O are retained as failed
  capacity observations: vanilla preempted active requests, while the chain
  methods returned capacity errors before completing the trajectory. No C=100
  throughput or speedup is inferred from those runs. Every speedup uses vanilla
  at the **same C** and the same 1.5× resident-row rule. The earlier vanilla
  C=16 run is a diagnostic and is not part of the matched comparisons.
- Every worker owns one whole trajectory. The first request has no synthetic
  wait; subsequent requests use a deterministic uniform pause in `[0, 2)`
  seconds derived from seed 42, instance ID, and turn. The exact same pause
  schedule is used for each method. These are synthetic tool waits,
  not the original estimated client/tool delays.
- Before timing, `prepare_forced_trace.py` renders every adjacent prompt with
  the target model tokenizer. It requires exact token prefix agreement and
  verifies that the assistant answer plus Chain Cache append suffix reconstructs
  the following full prompt.
- The primary metrics are complete replay wall time, total output tokens divided
  by that time, and non-streaming HTTP request latency percentiles. Report cache
  reuse from each response's `usage.prompt_tokens_details.cached_tokens` and
  require nonzero observed reuse. A configured cache alone is not evidence of
  a hit. Each case starts a fresh full-run server after a one-request smoke on
  a separate server process.

## Cache semantics

The forced token is written at the model sampling boundary before async device
feedback and host sequence postprocessing. Both dense and sparse servers use
the same forcing path. Radix methods send each recorded full prompt; Chain Cache
methods send the server-returned `chain_id` and an append index on later turns.
The runner requires `created` on the first turn and `resumed` afterward. If an
idle chain was evicted and the server returns `410 chain_gone`, the client makes
one recorded-full-prompt retry and requires a new `created` response, as the
MiniSWE client does. The retry time stays inside that turn's latency; recovery
counts are reported separately. Successful replay also requires nonzero cached
tokens in response usage. A configured cache alone is not evidence of a hit.

This protocol keeps the model forward and sampler work but adds a forced-token
device write each step. Forced text is never presented as the model's natural
solution behavior.

## Run one case

Activate the selected environment through `VENV_ACTIVATE`, or through
`CONDA_BASE` and `CONDA_ENV_PATH`. Prepare the forced workload on the data disk:

```bash
python scripts/official_experiments/agent_trace_sparse_methods/prepare_forced_trace.py \
  --trace "$TRACE_DIR" --model "$GLM_MODEL" --output "$GLM_FORCED"
```

Pass an existing checkpoint, pinned trace, and prepared workload:

```bash
CONDA_BASE="$CONDA_BASE" CONDA_ENV_PATH="$CONDA_ENV_PATH" \
AGENT_TRACE_SCRATCH_BASE="$SCRATCH_ROOT" \
SPARSEVLLM_MASTER_PORT="$MASTER_PORT" \
bash scripts/official_experiments/agent_trace_sparse_methods/run_case.sh \
  glm47 "$GLM_MODEL" vanilla-prefix 40 "$OUTPUT_ROOT" "$TRACE_DIR" \
  "$GPU_PAIR" "$PORT" full "$GLM_FORCED"
```

Use `smoke-only` instead of `full` for preflight. Give smoke and full runs
different output roots; the runner refuses to overwrite an existing case.
`run_matrix.sh` and `queue_matrix.sh` accept optional `METHOD:CONCURRENCY`
arguments after their existing positional arguments. Set
`AGENT_TRACE_ARCHIVE_REQUEST_LOGS=1` for a multi-case run on a filesystem with
limited inodes. After each server stops, the matrix runner verifies a tar archive
against the loose per-request JSON logs before replacing them with the archive.
For a separate SnapKV C=80 run with decode eviction enabled, set
`AGENT_TRACE_SNAPKV_DECODE_EVICTION=1` on `run_case.sh` and select
`snapkv-chain 80`. The runner freezes the current default eviction interval
(1,024 tokens) in `effective_setting.json` and the generated `engine.json`.
Use a new output root so the earlier C=80 capacity failure remains available.
Accept the rerun only if it completes all 8,000 requests with observed chain
reuse and zero preemptions or recompute replays.
For an H2O C=80 run aligned with the H20 SWE-lite quality evaluation, set
`AGENT_TRACE_H2O_SWELITE_SETTING=1` and select `h2o-chain 80` in a separate
output root. This freezes FP32 logits prefill scoring, no decode eviction,
16K prefill chunks, and `favor_min_decoding_seqs=48`. The trace protocol still
sets the resident-row limit to 120; the SWE-lite evaluation used 80. Treat this
as a separate performance variant from the probability-scoring H2O replay.
The initial matrix runner covers vanilla, OmniKV, and QuEST at C=40, plus
vanilla, SnapKV, and H2O at C=100, for GLM only. The matched follow-up uses
the same case runner at C=40 for all four sparse methods. The case runner saves
`run.log`, `status.tsv`, the engine
config, server manifest, smoke result, request artifacts, and replay summary
under `<OUTPUT_ROOT>/<model>_<method>_c<C>/`. Large artifacts stay on the
persistent data disk. Place finalized compact results in this directory with
device identity, launch arguments, Git commit, and measured results.

When fewer than two GPUs are idle, `queue_matrix.sh` waits for up to six hours
and selects one idle pair for the whole GLM matrix. It records
`queue_status.tsv`, `gpu_pair.txt`, and `queue.log` under the passed output root.
It exits without running a case if the GPU wait expires.

An accepted result requires all requests in the selected manifest to succeed, exact requested
completion counts, nonzero cached-token reuse, and zero active-request
preemptions and recompute replays. The preferred evidence is the final worker-load
snapshot. Runs started before that snapshot was added use an explicitly selected
complete server log with the manifest's finish-record count and zero unconditional
preemption/recompute warning records. Check method-specific rank
logs for actual CUDA Graph execution and failures before publishing speedups.
